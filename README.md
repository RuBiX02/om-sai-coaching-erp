# Om Sai Coaching ERP — Phase 3

A server-rendered Java web application for managing the day-to-day
operations of a small coaching institute: courses, subjects, batches,
students, enrollments (with batch-transfer history), login accounts,
**class sessions with attendance history and reports**, **fee
agreements**, **append-only payments with printable receipts**, and
**outstanding/collection summaries**.

Everything is honest, working software: there is no REST API, no React
front end and no extra layers beyond what the management screens need.
The UI templates are plain Bootstrap on the server side, with only a tiny
amount of vanilla JavaScript for progressive enhancement.

## Prerequisites

- **Java 25** (`JAVA_HOME` must point to a JDK 25 — see `pom.xml`, `<java.version>25</java.version>`)
- **PostgreSQL** (tested with 16+; any recent version works)
- **Maven** is *not* required: the included Maven Wrapper (`./mvnw`) is used for
  every command below.
- Docker is **not** required or used (Testcontainers was not used for tests in
  this phase — see PROJECT_STATUS.md).

## 1. Prepare the database

Create two PostgreSQL databases: `omsai` (application) and `omsai_test`
(integration tests run against this one and never touch `omsai`).

```bash
createdb omsai
createdb omsai_test
# or inside psql:
#   CREATE DATABASE omsai;
#   CREATE DATABASE omsai_test;
```

The real-browser tests (section 7) additionally use a third, disposable
database `omsai_browser` — `createdb omsai_browser` if you plan to run
them. The application schema is created entirely by Flyway at startup
(`V1__init.sql`, then `V2__attendance_and_fees.sql` for sessions,
attendance and fees). The Hibernate dialect is `validate` only — no
schema is ever generated by Hibernate.

## 3. Run the application

```bash
./mvnw spring-boot:run
# or
./mvnw package && java -jar target/coaching-erp-0.1.0.jar
```

Then open <http://localhost:8080/>. You will be redirected to the login
page.

## 4. First administrator account (bootstrap)

The application never ships with a hard-coded password. To create the
first administrator on a fresh database, start the application once with
opt-in environment variables:

```bash
APP_BOOTSTRAP_ADMIN=true \
APP_ADMIN_NAME="Om Sai Administrator" \
APP_ADMIN_EMAIL=admin@omsai.local \
APP_ADMIN_PASSWORD='Choose-A-Strong-Password#2026' \
./mvnw spring-boot:run
```

- The runner is **idempotent**: if any ADMIN account already exists, it
  does nothing.
- The password is used only from the environment (never written to Git or
  logs) and stored as a BCrypt hash.
- **Please sign in and change this password soon** (via an account
  administrator once it is set up).

After that, further accounts are managed in the UI (Accounts → add user),
always requiring email confirmation of the linked person.

## 5. Test the application

```bash
./mvnw test
```

The integration tests run against the `omsai_test` database (see
`src/test/resources/application-test.yml`; override `TEST_DB_URL`,
`TEST_DB_USERNAME`, `TEST_DB_PASSWORD` for a different disposable
PostgreSQL). Tests roll back their own data, so they are safe to re-run
(the only exception is the payment-concurrency test, which commits two
real rows to race threads and removes them again in its `@AfterEach`).

## 6. End-to-end smoke test (optional, needs a running app)

`scripts/e2e-smoke.sh` drives the real application over HTTP with curl
(respecting CSRF and session cookies) and verifies the main flows:

```bash
# start the app (with a bootstrap admin, only needed once) in one terminal:
APP_BOOTSTRAP_ADMIN=true \
APP_ADMIN_NAME="Om Sai Administrator" \
APP_ADMIN_EMAIL=admin@omsai.local \
APP_ADMIN_PASSWORD='DevAdmin#2026#Pass' \
./mvnw spring-boot:run

# in another terminal:
zsh scripts/e2e-smoke.sh
```

The script creates only `E2E …`-prefixed temporary data (timestamped, so
re-runs are safe), exercises 127 checks (login, CSRF, validation errors,
enrollment rules, transfers, withdraw/complete, teacher access, rate
limiting, logout, plus the whole Phase 2 surface: fee agreements,
payments and receipts down to the VOIDED stamp, class sessions,
attendance, cancel/complete rules, attendance reports and the teacher
session-ownership carve-out) and finishes with a summary line.

## 7. Real-browser tests (Playwright)

`scripts/e2e-smoke.sh` verifies HTTP behaviour, but only a real browser
can verify what users actually see: rendering, JavaScript behaviour,
console errors, print output. Those are covered by a Playwright for Java
suite (13 tests in `src/test/java/com/omsai/coaching/browser/`) that
boots the whole Spring application on a random HTTP port, drives a real
headless Chromium, and asserts on the live DOM.

Prerequisites:

- PostgreSQL databases `omsai_test` and `omsai_browser` (both disposable;
  the browser profile never touches `omsai`). `omsai_browser` can always
  be wiped and rebuilt with `zsh scripts/reset-browser-db.sh`.
- A Chromium-family browser. First use downloads one automatically via
  the Playwright driver (into `~/.cache/ms-playwright`):

  ```bash
  mvn -q -Pbrowser-tests -DskipTests exec:java -e \
    -Dexec.mainClass=com.microsoft.playwright.CLI \
    -Dexec.args="install chromium"
  ```

- As an alternative to the download, point the suite at a system browser
  with `PW_BROWSER_CHANNEL=chromium` or `PW_BROWSER_EXECUTABLE=/usr/bin/chromium`.

Run them:

```bash
./mvnw test                     # unit/service tests only (browser excluded)
./mvnw test -Pbrowser-tests     # unit + real-browser suite (155 tests total)
```

Run a single browser class: `./mvnw test -Pbrowser-tests -Dtest=AttendanceBrowserTest`.

What the suite covers: authentication (valid/invalid login, protected
pages, logout), sidebar navigation per role, course form validation,
attendance journeys (admin creates sessions, records attendance,
completes/cancels, reads reports; teachers work only on their own
sessions and are blocked elsewhere), fee agreements with partial
payments, receipts — including **print verification** under Chromium's
print media emulation (`page.emulateMedia({media: "print"})`) and
`page.pdf()` whose text is parsed with Apache PDFBox — and VOIDED
receipt rendering.

Every failure automatically writes diagnostics to
`target/browser-artifacts/`: a full-page screenshot, the captured
console log, unexpected HTTP responses and the failing assertion. The
receipt tests also write their screen/print screenshots and the two
generated PDFs there on every run, so you can open
`target/browser-artifacts/receipt-printed.pdf` and see exactly what
users would print.

Data safety: each browser test seeds only its own rows through the
`Fixtures` support class, tracks their IDs and deletes exactly those
rows afterwards (FK order respected); the bootstrapped
`browser-admin@omsai.test` account and all rows created before the test
run stay untouched. The suite additionally refuses to start unless the
database it is connected to is named `omsai_browser*` (checked against
the live connection, not the configured URL), so an accidental
`BROWSER_TEST_DB_URL` override cannot point it at `omsai` or
`omsai_test`.

## Domain rules implemented (Phases 1 and 2)

- **Courses** hold **subjects** (many-to-many through `course_subjects`).
- **Batches** belong to exactly one course (never changes), carry an
  academic year and optional dates; the course/year/name triple is unique.
- A batch may teach only **course subjects of its own course**
  (`batch_subjects`).
- **Teachers** may optionally link to a TEACHER login account
  (one-to-one). Inactive teachers cannot receive new assignments;
  reactivation restores eligibility. Assignments are never deleted.
- **Students** get a unique generated code like `OMS-2026-00001`.
- **Enrollments** are append-only history rows: ACTIVE → COMPLETED or
  WITHDRAWN. At any time a student holds at most one ACTIVE enrollment
  *per batch* and at most one ACTIVE enrollment *per course*
  (enforced both in the service and by partial unique indexes in the DB).
- Changing batches inside one course is a **transfer**: the previous
  ACTIVE record is closed as COMPLETED and a new ACTIVE record is created
  in the same transaction — the history is never deleted or rewritten.
- Inactive students/courses/batches reject new enrollments; inactive
  students reject transfers as well.
- A course subject that is (still) taught in a batch cannot be removed
  from the course — removal protection preserves teaching history.

## Phase 2 rules (sessions, attendance, fees)

- A **class session** is one class on one date for one batch-subject
  assignment (no recurring timetable). Its batch/course/subject context
  derives from the assignment, so records cannot drift.
- Lifecycle: OPEN → **COMPLETED** or OPEN → **CANCELLED**. Records are
  never deleted or erased; completed sessions reject edits, and a
  session that already has attendance rows cannot be cancelled.
- **Attendance** is tied to an enrollment, uniqueness per
  (session, enrollment) at the DB level; corrections update in place.
  The enrollment must belong to the session's batch and its effective
  period must cover the session date, so transferred students keep
  correct history.
- Reports (per student / per batch / per subject / per date) count only
  **completed** sessions inside each enrollment's period.
  Percentage = (present+late)/(present+late+absent)×100; EXCUSED is
  excluded and shows as "insufficient data" (never a fake 0%).
- **Fee agreements** are per (student, course, academic year) with money
  as BigDecimal/NUMERIC(12,2); discount cannot exceed the gross fee; a
  same-course batch transfer **reuses** the existing agreement in one
  transaction; amounts lock once any payment is recorded.
- **Payments** are append-only. Voiding records who/when/why and
  recalculates the balance; receipt numbers come from the database
  sequence `payment_receipt_seq` (`OMS-RCP-2026-000001` style) — the
  sequence never depends on counting rows; overpayments are rejected
  with the exact outstanding balance; concurrent payments are serialized
  by a pessimistic lock on the fee account.

## Security model

- Session-based login with the `user_accounts` table; roles are
  `ADMIN` and `TEACHER`.
- `ADMIN`: full access to every management screen.
- `TEACHER`: read-only access to `/teacher` (assignments home), plus the
  ability to create/manage class sessions and attendance **only for the
  subjects assigned to their own linked active teacher profile** (both
  the URL rule and the service-level rules enforce it — hidden links are
  never the security boundary). Everything else — courses, batches,
  students, accounts, fees, payments, reports — is 403 for teachers.
- CSRF protection is on; all forms submit the token (Thymeleaf does this
  automatically).
- Login is rate-limited in-memory per username + client IP:
  5 failed attempts / 15 min → further POSTs to `/login` are redirected
  to `/login?locked` until the window expires. A successful login clears
  the counter. (Single-node only; see PROJECT_STATUS.md.)
- Strict security headers: CSP (no inline scripts or styles), HSTS,
  Referrer-Policy, `X-Frame-Options … frame-ancestors 'none'`.
